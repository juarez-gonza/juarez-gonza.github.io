
* Simplified =std::execution=

Compositional patterns over lazy curried CPS, as developed over the
last sections, are analogous in many ways to the control flow
mechanism proposed by =std::execution=:

- Callbacks are analogous to receivers.
  - Invoking =operator()= / =set_value= on them propagates results
    through the execution.
- Thunks are analogous to operation state.
  - They ensure redex data's lifetime until completion.
  - Once called / =start=-ed the redex is executed.
- Lazy curried CPS functions are analogous to senders.
  - They enclose computation, but do not execute it (lazy).
  - They are =connect=-ed to a callback / receiver.
- Compositional patterns are analogous to sender algorithms.
  - They are parameterized by lazy curried CPS functions / senders and
    return lazy curried CPS functions / senders.
  - They describe the way in which computations are composed.

We now procede to translate the developed compositional patterns into
a structure more alike that of =std::execution='s sender algorithms,
while we explain some of =std::execution= core terminology.

** Simplified =just=

The most basic sender algorithm is =just=.  The API for invoking
=just= is about the same as that of Listing (tbd-link)just -- main
difference being the standard decided to use a CPO to disable ADL.


The =just= algorithm is what =std::execution= categorizes as a *sender
factory*.  A sender factory does not have any input sender and it
outputs a sender.  So =just= must return a sender that makes use of
its data argument somehow, leading us to the following code.

#+NAME: listing:just-sender-factory-step-0
#+CAPTION: =just= sender factory (0 of 2)
#+BEGIN_SRC C++
  template<typename T>
  struct just_::snd;

  static constexpr auto just = [](auto x) { return just_::snd(x); };
#+END_SRC


To determine what the =just_::snd= sender is supposed to do, we can
procede by analogy with respect to the lazy curried CPS implementation
of Listing (tbd-link)just:

1. The constructed sender is analogous to a lazy curried CPS function
   that has been partially applied to its redex data.  The
   captured redex data become member variables to be initialized
   during sender construction.

2. The only thing that can be done to a constructed sender is
   =connect=-ing it to a receiver to produce an operation state
   (applying it to a callback to produce a thunk).

3. The operation state does something with the receiver and the redex
   data, so it is constructed from them.

#+NAME: listing:just-sender-factory-step-1
#+CAPTION: =just= sender factory (1 of 2)
#+BEGIN_SRC C++
  template<typename Rcv, typename T>
  struct just_::op;

  template<typename T>
  struct just_::snd {
      T x;
      template<typename Rcv>
      op<Rcv, T> connect(Rcv next) { return {next, x}; }
  };
#+END_SRC


Analogously to how invoking a thunk results in the application of the
callback to the captured data in Listing (tbd-link)just, =start=-ing
the operation state forwards the captured data to the receiver via its
completion channel: =set_value=.

#+NAME: listing:just-sender-factory-step-2
#+CAPTION: =just= sender factory (2 of 2)
#+BEGIN_SRC C++
  template<typename Rcv, typename T>
  struct just_::op {
    Rcv next;
    T x;
    void start() { next.set_value(x); }
  };
#+END_SRC


This concludes the implementation of =just= in the simplified
=std::execution= framework.

# Input senders
# of a sender algorithm are typically referred to as *children senders*
# of the output or *parent sender*.  The largely common case (but not
# universal) in =std::execution= is that computation represented by
# children senders is executed before the computation represented by
# their parent sender.  The sender algorithm that relates them describes
# the children-to-parent dependency (compositional pattern).  =just= has
# no children senders, so it does not depend on the output of any
# children.

# The code in Listing (tbd-link)justender-factory]] above is a direct
# application of the recently stated rule of thumb to Listing
# (tbd-link)just.  Because =just_::snd= has no children senders, it does
# not make sense for there to be a receiver =just_::rcv= -- there are no
# children senders to which it could be connected to.

** Simplified =then=

The =then= algorithm is what =std::execution= categorizes as a *sender
adaptor*.  The parameter list of sender adaptors consists of both
senders (one or more) and other parameters required to execute the
computation represented by the output sender.  The input senders are
said to be the *children senders* of the output sender.  Conversely,
the output sender is the *parent sender* of the input senders.  A
sender adaptor thus can be thought as describing the
children-to-parent relation, i.e. it is a compositional pattern
between senders.


From the preceding paragraph, we can deduce that =then= must return a
sender that makes use of the input sender and input invocable.


#+NAME: listing:then-sender-adaptor-step-0
#+CAPTION: =then= sender adaptor (0 of 3)
#+BEGIN_SRC C++
  template<typename Prev, typename F>
  struct then_::snd;

  static constexpr auto then = [](auto prev, auto f) {
    return then_::snd(prev, f);
  };
#+END_SRC

Similar to the =just= sender factory, the =then= sender adaptor
constructs its associated sender and does nothing else.  This is
usually the case for sender algorithms in =std::execution=.


To determine what the =then_::snd= sender is supposed to do, we can
procede by analogy with respect to the lazy curried CPS implementation
of Listing (tbd-link then)then:

1. The constructed sender is analogous to a lazy curried CPS function
   that has been partially applied to its redex data.  The
   captured redex data and the child sender become member
   variables to be initialized during sender construction.

2. The only thing that can be done to a constructed sender is
   =connect=-ing it to a receiver to produce an operation state
   (applying it to a callback to produce a thunk).

3. The operation state does something with the receiver, the redex
   data, and the child sender, so it is constructed from them.


#+NAME: listing:then-sender-adaptor-step-1
#+CAPTION: =then= sender adaptor (1 of 3)
#+BEGIN_SRC C++
  template<typename Rcv, typename Prev, typename F>
  struct then_::op;

  template<typename Prev, typename F>
  struct then_::snd {
      Prev prev;
      F f;
      template<typename Rcv>
      op<Rcv, Prev, F> connect(Rcv next) { return {next, prev, f}; }
  };
#+END_SRC

The =then= lazy curried CPS of Listing (tbd-link then)then, once invoked,
attached a callback to the input invocable parameter and began
execution of the resulting thunk.  In the context of =std::execution=,
the =then= adaptor would need an associated receiver.  This receiver
must be =connect=-ed to the child sender of =then_::snd= when
=then_::op::start= is invoked, resulting in an operation state that is
immedately invoked.

#+NAME: listing:then-sender-adaptor-step-2
#+CAPTION: =then= sender adaptor (2 of 3)
#+BEGIN_SRC C++
  template<typename Op>
  struct then_::rcv;

  template<typename Rcv, typename Prev, typename F>
  struct then_::op {
    Rcv next;
    Prev prev;
    F f;

    void start() {
      auto op = prev.connect(rcv<op>{this});
      op.start();
    }

    void complete(auto x);
  };
#+END_SRC

It is generally the case that a receiver is associated to a sender
when the computation represented by the sender depends on the result
of at least one of its children senders.


The code in Listing (tbd-link then)thenender-adaptor-step-2]] declares
=then_::op::complete= function template and constructs =then_::rcv=.
A common pattern in =std::execution= is for the receiver completion
channel's body to be a simple forwarding expression.  Anything more
complex is communicated back into its associated operation state via
member functions in the operation state (=then_::op::complete=).  This
is depicted in Listing (tbd-link then)thenender-adaptor-step-3]].


#+NAME: listing:then-sender-adaptor-step-3
#+CAPTION: =then= sender adaptor (3 of 3)
#+BEGIN_SRC C++
  template<typename Op>
  struct then_::rcv {
    Op* op;
    void set_value(auto x) { return op->complete(x); }
  };

  template<typename Rcv, typename Prev, typename F>
  void then_::op::complete(auto x) {
    next.set_value(f(x));
  };
#+END_SRC

** Simplified =let_value=


#+BEGIN_SRC C++
    namespace let_value_ {
      template<typename Op>
      struct intermediate_rcv {
        Op* op;
        void set_value(auto x) { return op->complete_intermediate(x); }
      };

      template<typename Rcv, typename Prev, typename MakeSnd>
      struct op {
        Rcv next;
        Prev prev;
        MakeSnd make_snd;

        void start() {
          auto op1 = prev.connect(intermediate_rcv<op>{this});
          op1.start();
        }

        void complete_intermediate(auto x) {
          auto op2 = make_snd(x).connect(next);
          op2.start();
        }
      };

      template<typename Prev, typename MakeSnd>
      struct snd {
        Prev prev;
        MakeSnd make_snd;

        template<typename Rcv>
        op<Rcv, Prev, MakeSnd> connect(Rcv next) { return {next, prev, make_snd}; }
      };
    } // namespace let_value_

    static constexpr auto let_value = [](auto prev, auto make_snd) {
      return let_value_::snd(prev, make_snd);
    };
#+END_SRC

  namespace sync_wait_ {
    template<typename Ret>
    struct rcv {
      std::optional<Ret>* sink;
      void set_value(Ret x) { sink->emplace(x); }
    };
  } // namespace sync_wait_

  template<typename Ret>
  Ret sync_wait(auto prev) {
    std::optional<Ret> value;
    auto op = prev.connect(sync_wait_::rcv<Ret>{&ret});
    op.start();
    assert(value.has_value() and "Completion did not populate return value");
    return *value;
  };
