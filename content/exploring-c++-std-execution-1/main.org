* Continuation Passing Style

More concretely, C++ has no language construct that allows us to treat
continuations as any other kind of object in the language (some
languages do have such a construct, see [[https://scholarworks.iu.edu/dspace/items/52d1b603-67cd-4ba8-afbb-645cfdaa4f74/full][call/cc in Scheme]]).  What we
do have in C++ are function objects.  Being objects, they can be
constructed, destructed, used as function arguments, stored in data
structures, etc.


The core idea of this post is to leverage function objects as
representations of continuations.  This results in what is known as
*Continuation Passing Style* (CPS).  The program transformation that
turns code in /direct-style/ (the usual code, without continuations as
objects) into CPS is the *CPS transform*, which roughly corresponds to
the following algorithm:

1. Choose some expression =expr= in the program and consider an
   execution state where =expr= is the redex.
2. <<cps-transform:step-3>>From =expr=, write a *CPS function* (see
   Listing [[listing:cps-transform-step-3]]).  This is a function that:
   1. Parameterizes[fn:parameterize] the data on which =expr= depends,
      referred to as *redex data*.
   2. Takes one extra invocable parameter per continuation associated
      to =expr= in the original code, together referred to as
      *callbacks*.
   3. Applies /only one/ of the callbacks to the result of the
      evaluation =expr=.

#+NAME: listing:cps-transform-step-3
#+CAPTION: Direct style to Continuation Passing Style: Callee
#+BEGIN_SRC C++
  // Original code: Direct Style
  double sq(double x) { return x * x; }

  // After step 3: Continuation Passing Style
  auto sq(double x, auto cc) { return cc(x * x); }
#+END_SRC


3. [@3] Applies the CPS function to the data of =expr= that was
   parameterized by the CPS function, and to one lambda per callback
   parameter of the CPS function. Each lambda is associated to one of
   the continuations in the original code.  If the associated
   continuation is empty, then the body of the lambda just returns its
   argument (i.e. it is the identity function).  Otherwise, the body
   of the lambda corresponds to the steps of the associated
   continuation (see Listing [[listing:cps-transform-step-4]]).


#+NAME: listing:cps-transform-step-4
#+CAPTION: Direct style to Continuation Passing Style: Caller
#+BEGIN_SRC C++
  // Original code: Direct Style
  auto sqx = sq(x);
  return foo(sqx);

  // After step 4: Continuation Passing Style
  return sq(x, [&](double sqx) { return foo(sqx); });
#+END_SRC


4. [@4] <<cps-transform:step-4>> For each non-identity lambda created
   in step 4, repeat from step 2 using as =expr= the first statement
   of the lambda.

To illustrate the iterative nature of the CPS transform ([[cps-transform:step-4][step 4]]),
consider the following example:

#+NAME: listing:hypotenuse
#+CAPTION: Hypotenuse function written in direct style
#+BEGIN_SRC C++
double sq(double x) { return x * x; }
double add(double x, double y) { return x + y; }
double sqr(double x) { return sqrt(x); }
double hypotenuse(double x, double y) {
  auto sqx = sq(x);
  auto sqy = sq(y);
  auto r = add(sqx, sqy);
  return sqr(r);
}
#+END_SRC

A few iterations of the CPS transform yield

#+NAME: listing:cps-hypotenuse
#+CAPTION: Hypotenuse function written in CPS
#+BEGIN_SRC C++
double sq(double x, auto cc) { return cc(x * x); }
double add(double x, double y, auto cc) { return cc(x + y); }
double sqr(double x, auto cc) { return cc(sqrt(x)); }
double hypotenuse(double x, double y, auto cc) {
  return sq(x, [&](double sqx) {
    return sq(y, [&](double sqy) {
      return add(sqx, sqy, [&](double r) {
        return sqr(r, cc);
      });
    });
  });
}
#+END_SRC

Ignoring the involved syntax of the resulting code, it is not hard to
see that callbacks have effectively given us a way to deal with
continuations as first-class objects.


[fn:parameterize] It would be more correct to say "abstracting over the
free variables of =expr=". Or even "performing a [[https://matt.might.net/articles/closure-conversion/][closure conversion]]",
but "parameterizing" is more widely used in the C++ ecosystem,
therefore for the intended audience of this post (hopefully).


Of course one does not perform all of this callback ritual for silly
arithmetic expressions as we have done so far, but rather when the
redex can be resolved asynchronously. In such cases it is beneficial
to place the callback in a data structure (queue) so that the program
can do other stuff while the redex is being resolved.  Once completion
of the redex is signaled (somehow) and the result is gathered
(somehow), the stored callback can be retrived and applied to the
result of the redex.

** What about =main=?
<<subsec:what-about-main>>

In the ideal CPS world, everything in a program that is written in CPS
takes these callback arguments.  In practice this is rarely the case,
because most of us have to deal with =main= being the entrypoint of
our programs.  The signature of =main= cannot be modified, so =main=
being the entrypoint is at odds with our ideal CPS world.


The solution is simple: use =main= as a barrier between the CPS world
and the direct style world.

#+NAME: listing:main-for-cps
#+CAPTION: Bridging CPS and direct style in =main=
#+BEGIN_SRC C++
void main() {
  std::optional<double> result;
  hypotenuse(2.0, 3.0, [&](double res) { result = res; });
  std::println("{}", *result);
}
#+END_SRC

Breaking the ideal CPS world feels a bit dirty.  This is C++, we
should be used to this feeling.
