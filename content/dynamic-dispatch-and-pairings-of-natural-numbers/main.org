#+title: State machines, dynamic multi-dispatch, and pairings of natural numbers

Recently at work I had to write a finite state machine in C++20. At
the expense of being redundant due to the target audience of this
post, a state machine evolves over time by changing its internal state
each time it is fed some input. Having to execute logic based on
/both/ the current state and the input being fed implies
implementations must use some kind of /dynamic multi-dispatch/
technique.


In C++ there are well-known approaches to implement state machines
using [[https://khuttun.github.io/2017/02/04/implementing-state-machines-with-std-variant.html][=std::variant= and =std::visit=]].  It is also possible to
implement state machines with inheritance-based dynamic polymorphism
using something like the [[https://www.spigotmc.org/threads/implementing-finite-state-machines-with-visitor-design-pattern.336273/][visitor pattern]].  My problem was that due to
circumstances of life and past decisions (of my authoring) the
dispatch mechanism I had to implement was not based on types, but
based on =enum= values.


I solved this problem using some maths and metaprogramming which I
will present throughout this post. After presenting the solution for
the binary case, I will also present its full generalization to
dynamic dispatch based on an arbitrary number of =enum=.


* Problem setup

In order to have something concrete in mind, we will use the finite
state machine (FSM) described by the transition table below

| State\Event   | a | b | c |
|---------------+---+---+---|
| A (initial)   | A | B | C |
| B             | B | C | D |
| C             | C | B | D |
| D (final)     | - | - | - |

where '-' is used to indicate that there are no transitions from the
=(state, input)= pair of the given row and column.  Reaching such
transitions is considered an error.  Alternatively, we could make an
error state and have several final states.  Representing errors in one
way or the other would not affect our multi-dispatch solution, so we
wont be wasting any more time in the finer details of the FSM
construction.

From the signature of =dispatch_enum= we can already come up with a
rough plan to achieve what we want.

1. Compile time work
   1. List the values enumerated by =StateT= and =InputT=, denote them
      =states= and =inputs=, respectively.

      # - If using C++26's reflection, then this is quite straightforward.

      # - Another option is to require the user to provide some
      #   compile-time constant where the values are listed and make that
      #   list queryable via some class-specialization hook. This poses
      #   either a burden on maintainability or requires using [[https://www.reddit.com/r/cpp/comments/110ddo1/comment/j88qt0g/?utm_source=share&utm_medium=web3x&utm_name=web3xcss&utm_term=1&utm_content=share_button][macros]] of
      #   some sort to ensure consistency of enumerated values between
      #   =enum= definition and the definition of the associated list of
      #   values.

      # - Use the infamous [[https://github.com/Neargye/magic_enum][magic_enum]] library. This is the approach we will
      #   follow as it provides the most ergonomic solution for C++20, at
      #   the expense of some compilation time maybe.

   2. Map each value in =states= to a distinct =integral=.  Do the
      same with =inputs=.  Notice one input and one state may share a
      mapping value. Denote that mapping function by =u=.

      # - This function in principle could be anything that satisfies these
      #   requirements. =iota= would do the trick, but we would need to
      #   keep some compile time dictionary to know which enum value
      #   corresponds to said index.  Moreover, at a later stage the
      #   runtime values =state= and =input= must be converted by $g$, so
      #   it should have a time complexity of $O(1)$ as it will execute at
      #   runtime and must not pessimize what a standalone =switch=
      #   lowering would have emmited from switching on the =enum=
      #   itself. It is at this last point where =iota= would fail, as it
      #   would require some sort of search over the list of values of the
      #   =enum= on every case, whereas the compiler lowering of a =switch=
      #   only does such searches in adverse code generation cases.

      # - Since we have restricted our work to =unsigned integral=, we
      #   could just rely on the underlying type representation of the
      #   =enum=.  If the =enum= values themselves are sparse, then this
      #   approach would inherit that problem into the generated
      #   =switch=. In any case, the user wouldn't be any better
      #   hand-rolling the =switch= as the same problem would arise.

   3. Obtain the cartesian product of the lists of =integral= values
      from the previous step.

   4. Encode each pair in the cartesian product to a unique =integral=
      using an encoding function =e=.  Denote the resulting list by
      =encodings=.

      The last three steps can be summarized in a mathematical formula
      as obtaining the set

      \[\{ e(u(state), u(input)) : state \in StateT, input \in InputT\}.\]

   5. Construct a dispatching mechanism (=switch=) based
      on a single runtime value, using =encodings= as the
      discriminants (=case= labels).

   6. Inside each =case=, where the associated label =l= is known at
      compile time, use the inverse of the encoding function =e= and
      the inverse of =u= to obtain compile time values =(x, y)= such
      that =e(u(x), u(y)) = l=, and invoke the argument function =f=
      using =enum_values= tags constructed from =x= and =y=.

2. Runtime work

   1. Obtain the encoding of the input arguments =encoded =
      e(u(state), u(input))=.

   2. Dispatch using =encoded= as the sole argument on which branching
      is based.


* Math

In order to solve the encoding problem in which we convert a decision
based on two =integral= values into a decision based on one =integral=
value we need some math.  To simplify the problem a bit we will
disregard negative values (i.e., we will work with =unsigned
integral=).


If we ignore the fact that computers work with fixed-width integers,
then we could consider the (unsigned) underlying type of an =enum= to
be the set of natural numbers $\mathbb{N}$ (including $0$).  This
allows us to express the encoding problem in mathematical terms as the
problem of finding a function from the set of pairs of natural numbers
$\mathbb{N} \times \mathbb{N}$ to $\mathbb{N}$ which is /invertible/
--- the invertibility requirement is crucial for the implementation
strategy layed out in the next section.


Functions with these characteristics are well-known objects in
mathematics, called [[https://en.wikipedia.org/wiki/Pairing_function][pairing functions]].  There are [[https://drhagen.com/blog/superior-pairing-function/][many pairing
functions]].  I considered the following:

- Pairing based on the [[https://en.wikipedia.org/wiki/Fundamental_theorem_of_arithmetic][Fundamental Theorem of Arithmetic]] (FTA).  This
  pairing function uses the fact that any integer greater than $1$ has
  a unique representation as a product of powers of primes.  Such a
  pairing $f$ can be defined as

  \[
     f : \mathbb{N} \times \mathbb{N} \to \mathbb{N},\quad f(a,b) := 2^a 3^b.
  \]

  After staring at the definition of $f$ for a while, it is clear that
  we cannot use this pairing for at least two reasons:

  1. First, the range of $f$ is too sparse. Two numbers in the range of
     $f$ have a gap between them of at least a factor of $2$ between
     them.  This is unlikely to encourge the emision of jump tables.

  2. The second problem is related to the finite nature of computers.
     If we worked with =std::uint64_t=, trouble would arise when the
     sum of the =enum= values $a$ and $b$ being mapped is equal to or
     greater than $64$ because

     \[ f(a,b) \geq 2^a3^b \geq 2^{a+b} \gt 2^{64}-1, \]

     i.e., =std::uint64_t= would be overflown! $\mathbb{N} \neq$ =std::uint64_t=.

  (For those interested in the inverse $f^{-1}$, I recommend the
  introductory chapters on recursive functions in
  [[https://www.cambridge.org/core/books/computability-and-logic/440B4178B7CBF1C241694233716AB271][Computability
  and Logic by Boolos, Burgess, & Jeffrey 5th ed]])
