#+title: State machines, dynamic multi-dispatch, and pairings of natural numbers

Recently at work I had to write a finite state machine (FSM) in
C++20. At the expense of being redundant for the target audience of
this post, lets recall that a state machine evolves over time by
changing its internal state each time it is fed some input. Having to
execute logic based on /both/ the current state and the input being
fed implies implementations must use some kind of /dynamic
multi-dispatch/ technique.


In C++ there are well-known approaches to implement state machines
using =std::variant= and =std::visit= (see [[https://khuttun.github.io/2017/02/04/implementing-state-machines-with-std-variant.html][Kalle Huttunen's post]],
[[https://github.com/mpusz/fsm-variant][Mateusz Pusz's library]], or similar).  It is also possible to do this
with inheritance-based dynamic polymorphism using something like the
visitor pattern.  The problem is that due to circumstances of life and
past decisions (of my authoring) the dispatch mechanism I had to
implement was not based on types, but based on =enum= values.


Using some mathematical and metaprogramming tricks the problem can be
solved and even extended to work for the n-ary case --- although maybe
the solution here presented is not something I'd recommend if
compilation times are of any concern at all, but I found this cool
anyways.


* The problem setup

In order to have something concrete in mind, we will use the FSM
described by the transition table below

| State\Event   | a | b | c |
|---------------+---+---+---|
| A (initial)   | A | B | C |
| B             | B | C | D |
| C             | C | B | D |
| D (final)     | - | - | - |

where '-' is used to indicate that there are no transitions from the
=(state, input)= pair of the given row and column, reaching such
transitions is considered an error.  We could make instead an error
state and have several final states. It would not affect our
multi-dispatch solution, so we wont be wasting any more time in the
finer details of the FSM construction.

* The math

In order to convert a decision based on two =integral= values into a
decision based on one =integral= value we need some math.  Before
doing so, however, we will further restrict the problem to work with
=unsigned integral= values (that is, no negative values).

The problem at hand now screams for a solution based on [[https://en.wikipedia.org/wiki/Pairing_function][pairing
functions]].  These functions are invertible functions between
$\mathbb{N}$ and $\mathbb{N} \times \mathbb{N}$. There are [[https://drhagen.com/blog/superior-pairing-function/][many
pairing functions]].  I considered the following:

- Pairing based on the [[https://en.wikipedia.org/wiki/Fundamental_theorem_of_arithmetic][Fundamental Theorem of Arithmetic]] (FTA).  This
  pairing function uses the fact that any integer greater than $1$ has
  a unique representation as a product of powers of primes.  Such a
  pairing $f$ can be defined as

  \[
     f : \mathbb{N} \times \mathbb{N} \to \mathbb{N},\quad f(a,b) := 2^a 3^b.
  \]

  After staring at the definition of $f$ for a while, it is clear that
  we cannot use this pairing for at least two reasons:

  1. First, the range of $f$ is too sparse. Two numbers in the range of
     $f$ have a gap between them of at least a factor of $2$ between
     them.  This is unlikely to encourge the emision of jump tables.

  2. The second problem is related to the finite nature of computers.
     If we worked with =std::uint64_t=, trouble would arise when the
     sum of the =enum= values $a$ and $b$ being mapped is equal to or
     greater than $64$ because

     \[ f(a,b) \geq 2^a3^b \geq 2^{a+b} \gt 2^{64}-1, \]

     i.e., =std::uint64_t= would be overflown! $\mathbb{N} \neq$ =std::uint64_t=.

  (For those interested in the inverse $f^{-1}$, I recommend the
  introductory chapters on recursive functions in
  [[https://www.cambridge.org/core/books/computability-and-logic/440B4178B7CBF1C241694233716AB271][Computability
  and Logic by Boolos, Burgess, & Jeffrey 5th ed]])

- The [[https://en.wikipedia.org/wiki/Pairing_function#Cantor_pairing_function][Cantor pairing function]].  To my knowledge the oldest pairing
  function. It can be visualized in the a 2D graph as a walk through
  the diagonals of the graph.

\end{equation*}

From this signature we can already come up with a rough plan to
achieve what we want.

1. Compile time work
   1. For each =enum= (=StateT=, =InputT=), list the values it
      enumerates.

      # - If using C++26's reflection, then this is quite straightforward.

      # - Another option is to require the user to provide some
      #   compile-time constant where the values are listed and make that
      #   list queryable via some class-specialization hook. This poses
      #   either a burden on maintainability or requires using [[https://www.reddit.com/r/cpp/comments/110ddo1/comment/j88qt0g/?utm_source=share&utm_medium=web3x&utm_name=web3xcss&utm_term=1&utm_content=share_button][macros]] of
      #   some sort to ensure consistency of enumerated values between
      #   =enum= definition and the definition of the associated list of
      #   values.

      # - Use the infamous [[https://github.com/Neargye/magic_enum][magic_enum]] library. This is the approach we will
      #   follow as it provides the most ergonomic solution for C++20, at
      #   the expense of some compilation time maybe.

   2. For each =enum=, map each value it enumerates to a distinct
      =unsigned integral=.  Denote that mapping function by $g$ and
      note the restriction of inupts being mapped to /distinct/
      outputs makes it invertible.

      # - This function in principle could be anything that satisfies these
      #   requirements. =iota= would do the trick, but we would need to
      #   keep some compile time dictionary to know which enum value
      #   corresponds to said index.  Moreover, at a later stage the
      #   runtime values =state= and =input= must be converted by $g$, so
      #   it should have a time complexity of $O(1)$ as it will execute at
      #   runtime and must not pessimize what a standalone =switch=
      #   lowering would have emmited from switching on the =enum=
      #   itself. It is at this last point where =iota= would fail, as it
      #   would require some sort of search over the list of values of the
      #   =enum= on every case, whereas the compiler lowering of a =switch=
      #   only does such searches in adverse code generation cases.

      # - Since we have restricted our work to =unsigned integral=, we
      #   could just rely on the underlying type representation of the
      #   =enum=.  If the =enum= values themselves are sparse, then this
      #   approach would inherit that problem into the generated
      #   =switch=. In any case, the user wouldn't be any better
      #   hand-rolling the =switch= as the same problem would arise.

   3. Obtain the cartesian product of the lists of =unsigned integral=
      values from the previous step.

   4. Map each element in the cartesian product to a single =unsigned
      integral= using =szudzek_pair=.

   5. Use the resulting list of =unsigned integral= to construct a
      =switch= based on a single runtime vaulue.

   6. Since the associated value to a =case= is constant, use
      =szudzek_unpair= and the inverse of $g$ to obtain compile time
      values $(x, y)$ for each possible =case= label, and invoke the
      argument function =f= using =integral_constant= tags constructed
      from $x$ and $y$.

2. Runtime work

   1. Obtain the encoding, =encoded=, of the arguments by applying $g$
      separately to each argument and invoking =szudzek_pair= on the
      resulting =unsigned integral= values.

   2. Dispatch using =encoded= as the sole argument on which branching
      is based.
