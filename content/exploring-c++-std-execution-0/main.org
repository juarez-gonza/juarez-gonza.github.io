This post is the first entry in a series of posts dissecting C++
=std::execution=: the framework for asynchronous computation proposed
for standardization.  The main purpose of the series is to develop an
understanding of =std::execution='s API and (my understanding of) the
rationale behind it from first principles.  Additionally, those who
have already studied =std::execution= and found themselves in one of
the first four [[https://en.wikipedia.org/wiki/Five_stages_of_grief][stages of grief]] when analyzing the meaning of
- "Senders represent pending work",
- "Senders compose",
- "Users rarely need to care about receivers", or
- "=let_value= is /just/ the bind operator of the Continuation monad",
may find this series useful to reach the acceptance[fn:dislike] stage.


[fn:dislike] The reason I dislike the sentences in the bullet points are,
in order of appearance:
- What is "work"? Is it measured in Joules? What is "pending"?
  Potential energy?
- How is composition defined in sender-land?
- Not seeing directly in code is /not/ the same as not caring.
- Waving the Continuation monad around to C++ programmers without
  explaining it is lazy at best. Moreover, the model of
  =std::execution= is much more than /just/ the Continuation monad --
  hence =let_value= is much more than /just/ the bind operator of the
  Continuation monad.


We begin with the bare basics: continuations and the structure of
computation under a simplified =std::execution= framework.  We will
add complexity to the framework as the series progresses, slowly
converging to =std::execution= as proposed for standardization.


* Computation and continuations

A computation can be intuitively defined as a process by which some
inputs are converted into some outputs by executing a set of steps one
after the other[fn:computation-model].  At any given time, the execution
state of a computation can be subdivided into two: already executed
steps and to-be-executed steps.  To-be-executed steps can be further
subdivided into the next /immediate/ step to be executed, and the
remaining /non-immediate/ steps to be executed.  The former step is
known as the *reducible expression* (redex for short) and the latter
steps conform what is referred to as the *continuation*.


[fn:computation-model] A more theoretical definition would involve a
model of computation such as Turing machines, general recursive
functions, or lambda calculus.  But it is not the intention of this
post to be as precise with these details when the general idea can be
(almost) entirely captured by simpler terminology.


The wording of the previous paragraph is intentionally vague.  This is
to prevent its understanding in terms that are too concrete for the
level of reasoning we are aiming for.  If in place of the word "steps"
the paragraph used the word "instructions", then for us programmers
this could be easily (mis)understood as a definition of reducible
expressions and continuations in terms of CPU instructions.  While CPU
instructions could be thought of as steps, they are far from the only
abstraction level at which we would like to apply these ideas.  The
following examples should clarify the situation.


** Example 1: Arithmetic expressions

Given the expression =1 + 2 * 3=, the usual precedence rules tell us
that the first step to be executed is =2 * 3=.  That is, =2 * 3= is
the redex and =1 + ...= is the continuation.


While =2 * 3= is executed, the result of =1 + ...= remains
undetermined.  We can think of =1 + ...= as being /suspended/ until
the result of =2 * 3= is available.  Once the result is available, we
substitute the ellipsis in =1 + ...= to obtain =1 + 6=.  This
substitution process is denoted as /applying the continuation/.


The expression we are left with, =1 + 6=, has one single step to be
executed and an empty continuation (no non-immediate next steps).  In
other words, after executing the redex, the computation is /done/.


This silly example already shows a key property of continuations: they
are comprised not solely of operational descriptions (=+=), but also
of the data needed to execute these operations once the continuation
is applied (=1=).

** Example 2: Subsequent statements

There is no reason to limit the abstraction level of "steps" just to
arithmetic expressions.  We could take a step to be a statement.  The
order of execution is given by the usual top-to-bottom statement
execution.


Consider

#+NAME: listing:example-2
#+CAPTION: Example 2
#+BEGIN_SRC C++ -n
  auto sqx = x * x;
  auto sqy = y * y;
  auto r = sqx + sqy;
#+END_SRC

A valid execution state has the statement in line 1 as its redex and
statements of lines 2 and 3 conform its continuation.


Disregarding practicality, it does not really matter how granular
(abstract) a step is when discussing continuations as long as we are
consistent.

** Example 3: Function boundaries

So far none of the examples have function calls in them, but this does
not have to be the case.  Given the function =hypotenuse= as defined
below

#+NAME: listing:example-3
#+CAPTION: Example 3
#+BEGIN_SRC C++ -n
double hypotenuse(double x, double y) {
  auto sqx = sq(x);
  auto sqy = sq(y);
  auto r = add(sqx, sqy);
  return sqrt(r);
}
#+END_SRC
If =sq(x)= is the redex of an execution state, then its continuation
is conformed by the assignment to =sqx=, statements of lines 5, 6 and
7, and whatever the caller of =hypotenuse= does after =hypotenuse=
returns.  Notice that we treated =sq(x)= as a single step, ignoring
the complexity of the implementation of =sq=.


The notion being stressed throughout these first three examples, is
that of continuations being "whatever remains to be executed",
regardless of the abstraction level at which we decide to operate in.


Before dealing with more interesting stuff, the final example displays
some more key properties of continuations.

** Example 4: Conditional branches
<<conditional-branches>>

Consider the code listing below.  What is the continuation when line
=1= is the redex?  Is it necessary to know the result of =rand() % 2=
to determine the continuation?

#+NAME: listing:example-4
#+CAPTION: Example 4
#+BEGIN_SRC C++ -n
  if (rand() % 2) {
    return foo();
  } else {
    return bar();
  }
#+END_SRC
This is a tricky question.  There is no such thing as /the/
continuation at this point in the execution, but rather two (!)
continuations.  After evaluating the conditional, one continuation is
/discarded/ and the other one is applied.


This example, short as it is, illustrates three more properties of
continuations: (1) there is not necessarily one continuation at any
given time; (2) continuations do not have to be applied, they can be
discarded; and (3) a continuation may be applied or discarded based on
runtime information.


* Continuation Passing Style


Continuations as shown in the examples so far are not very
interesting.  We have identified them as part of the structure of
execution state, but we cannot really /do/ anything with them.


The issue here is that C++ has no language construct that allows us to
treat continuations as any other kind of object in the language (some
languages do have such a construct, see [[https://scholarworks.iu.edu/dspace/items/52d1b603-67cd-4ba8-afbb-645cfdaa4f74/full][call/cc in Scheme]]).  What we
do have in C++ are function objects which can be passed around as
arguments to functions -- this is made easier by the existence of
lambdas.  So we are going to apply the following program
transformation throughout the whole program:

1. Start from the beginning of the program
2. Recognize the redex and its continuation.
3. <<cps-transform:step-3>>Replace the redex by a function that
   1. Takes the parameters needed to execute the redex.
   2. Takes one extra invocable parameter per continuation.
   3. Returns the result of applying only one of the invocable
      parameters of step 3.2 to the redex.
4. Invoke the function of step 3 with the arguments that allow the
   execution of the redex and as many lambdas as continuations.  The
   body of these lambdas correspond to the steps of the continuation
   to which they are associated.
5. For each non-empty lambda created in step 4, repeat the process
   from step 2 starting from the redex of an execution that begins at
   the first statement of the lambda.

To illustrate the result of this procedure, let us apply it to the
code below

#+NAME: listing:hypotenuse
#+CAPTION: Hypotenuse function written in direct style
#+BEGIN_SRC C++ -n
double sq(double x) { return x * x; }
double add(double x, double y) { return x + y; }
double sqr(double x) { return sqrt(x); }
double hypotenuse(double x, double y) {
  auto sqx = sq(x);
  auto sqy = sq(y);
  auto r = add(sqx, sqy);
  return sqr(r);
}
#+END_SRC

yielding

#+NAME: listing:cps-hypotenuse
#+CAPTION: Hypotenuse function written in CPS
#+BEGIN_SRC C++ -n
double sq(double x, auto cc) { return cc(x * x); }
double add(double x, double y, auto cc) { return cc(x + y); }
double sqr(double x, auto cc) { return cc(sqrt(x)); }
double hypotenuse(double x, double y, auto cc) {
  return sq(x, [&](double sqx) {
    return sq(y, [&](double sqy) {
      return add(sqx, sqy, [&](double r) {
        return sqr(r, cc);
      });
    });
  });
}
#+END_SRC

If we bare with the ugliness of the code above for a second, we may
notice that this process has effectively given us a way to deal with
continuations as first-class objects, referred to as *callbacks*.  The
technique that enables this is called *Continuation Passing Style*
(CPS) and the algorithm described above is the *CPS transform*.


Having the continuation be represented by object allows us to do
whatever one would do with an object (for example, store it in a
queue, call it a /task queue/).  Of course usually one does not
perform all of this callback ritual for silly arithmetic expressions,
but rather when the redex can be resolved asynchronously. In such
cases, it is beneficial to place the continuation in a data structure
(queue) so that the program can do other stuff while it waits for the
completion of the redex to be signaled in some form.  Once completion
is signaled and the result is gathered (somehow), the continuation can
be applied to it.

** What about =main=

In our ideal CPS world, everything in a program that is written in CPS
takes these callback arguments (there can be more than one callback,
see [[conditional-branches][Example 4]] and apply the CPS transform).  But most of us have to
deal with =main= being the entry point of our programs.  The signature
of =main= cannot be modified, putting it at odds with our idealized
CPS world.  The solution is simple: =main= acts as a barrier between
the CPS world and the direct style world.

#+NAME: listing:main-for-cps
#+CAPTION: Bridging CPS and direct style in =main=
#+BEGIN_SRC C++
void main() {
  std::optional<double> result;
  hypotenuse(2.0, 3.0, [&](double res) { result = res; });
  std::println("{}", *result);
}
#+END_SRC

Breaking the ideal CPS world feels a bit dirty.  This is C++, we are
used to this feeling.

* From CPS to =std::execution=

We are still a couple of program transformations away from the
simplified =std::execution= framework that was promised by the
introduction of this post.  It is convenient to have some running
example to which the described transformations are applied, so we are
going to start from the point we left off in the [[listing:cps-hypotenuse][CPS hypotenuse
example]].

** Getting a uniform shape

We have already seen how [[Cps-transform:step-3][step 3]] of the CPS transform creates a new
function whose parameter list holds two kinds of parameters:


1. The data that allows the execution of the redex.
2. The callbacks representing the continuations of the redex.


The purpose of the next transformation is to refactor each of these
newly created functions into a new one.  This new function is
structured so that the split between redex arguments and callback
arguments is evident.  [[Https://en.wikipedia.org/wiki/Currying][Currying]] the callback arguments achieves this
goal.  For the running example the result is shown below.

#+NAME: listing:curried-cps-hypotenuse
#+CAPTION: Hypotenuse function written in curried CPS
#+BEGIN_SRC C++ -n
double sq(double x) { return [=](auto cc) { return cc(x * x); }; }
double add(double x, double y) { return [=](auto cc) { return cc(x + y); }; }
double sqr(double x) { return [=](auto cc) { return cc(sqrt(x)); }; }
double hypotenuse(double x, double y) {
  return [=](auto cc) {
    return sq(x, [&](double sqx) {
      return sq(y, [&](double sqy) {
        return add(sqx, sqy, [&](double r) {
          return sqr(r, cc);
        });
      });
    });
  };
}
#+END_SRC

If we bare with the ugliness of the code above for a second, we may
notice that this achieves the clear split between parameters used by
the redex and the callbacks that represent the continuation.  Now
invoking a function written in *curried CPS* -- unlike CPS, this
nomenclature is non standard -- is two stepped:


1. First, the redex arguments get passed into the function.
2. Second, the callbacks representing the continuations get passed
   into the lambda returned by the function.


One can also think of the invocation of curried CPS functions in terms
of finite state machines (FSM):

- When no argument has been passed into the function, the FSM is in a
  *non-configured* state.

- When the function is applied to the redex arguments, the FSM
  transitions to a *disconnected* state.  At this point the redex has
  not yet executed, but all the information needed to do so is
  available.

- Finally, when the returned lambda is applied to the callback
  arguments, the FSM transitions to the *started* state.  Execution of
  the redex begins and one of the callbacks is applied to the result
  of the redex.

Before applying this transformation, each CPS function required us to
inspect its parameter list to figure out which parameters are required
by the redex and which are callbacks.  Now this is always known from
the structure of the curried CPS functions.  Such /uniformity/ is
really useful for the sorts of generic programming that is heavily
used throughout =std::execution=.
