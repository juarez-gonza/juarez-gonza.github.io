This post is the first entry in a series of posts dissecting C++ std::execution: the framework for asynchronous computation proposed for standardization. The main purpose of the series is to develop an understanding of std::execution's API and (my understanding of) the rationale behind it from first principles. Additionally, those who have already studied std::execution and found themselves in one of the first four stages of grief when analyzing the meaning of

  • "Senders represent pending work",
  • "Senders compose",
  • "Users rarely need to care about receivers", or
  • "let_value is just the bind operator of the Continuation monad",

may find this series useful to reach the acceptance1 stage.

We begin with the bare basics: continuations and the structure of computation under a simplified std::execution framework. We will add complexity to the framework as the series progresses, slowly converging to std::execution as proposed for standardization.

Computation and continuations

A computation can be intuitively defined as a process by which some inputs are converted into some outputs by executing a set of steps one after the other2. At any given time, the execution state of a computation can be subdivided into two: already executed steps and to-be-executed steps. To-be-executed steps can be further subdivided into the next immediate step to be executed, and the remaining non-immediate steps to be executed. The former step is known as the reducible expression (redex for short) and the latter steps conform what is referred to as the continuation.

The wording of the previous paragraph is intentionally vague. This is to prevent its understanding in terms that are too concrete for the level of reasoning we are aiming for. If in place of the word "steps" the paragraph used the word "instructions", then for us programmers this could be easily (mis)understood as a definition of reducible expressions and continuations in terms of CPU instructions. While CPU instructions could be thought of as steps, they are far from the only abstraction level at which we would like to apply these ideas. The following examples should clarify the situation.

Example 1: Arithmetic expressions

Given the expression 1 + 2 * 3, the usual precedence rules tell us that the first step to be executed is 2 * 3. That is, 2 * 3 is the redex and 1 + ... is the continuation.

While 2 * 3 is executed, the result of 1 + ... remains undetermined. We can think of 1 + ... as being suspended until the result of 2 * 3 is available. Once the result is available, we substitute the ellipsis in 1 + ... to obtain 1 + 6. This substitution process is denoted as applying the continuation.

The expression we are left with, 1 + 6, has one single step to be executed and an empty continuation (no non-immediate next steps). In other words, after executing the redex, the computation is done.

This silly example already shows a key property of continuations: they are comprised not solely of operational descriptions (+), but also of the data needed to execute these operations once the continuation is applied (1).

Example 2: Subsequent statements

There is no reason to limit the abstraction level of "steps" just to arithmetic expressions. We could take a step to be a statement. The order of execution is given by the usual top-to-bottom statement execution.

Consider 

1: auto sqx = x * x;
2: auto sqy = y * y;
3: auto r = sqx + sqy;

A valid execution state has the statement in line 1 as its redex and statements of lines 2 and 3 conform its continuation.

Disregarding practicality, it does not really matter how granular (abstract) a step is when discussing continuations as long as we are consistent.

Example 3: Function boundaries

So far none of the examples have function calls in them, but this does not have to be the case. Given the function hypotenuse as defined below 

1: double hypotenuse(double x, double y) {
2:   auto sqx = sq(x);
3:   auto sqy = sq(y);
4:   auto r = add(sqx, sqy);
5:   return sqrt(r);
6: }

If sq(x) is the redex of an execution state, then its continuation is conformed by the assignment to sqx, statements of lines 5, 6 and 7, and whatever the caller of hypotenuse does after hypotenuse returns. Notice that we treated sq(x) as a single step, ignoring the complexity of the implementation of sq.

The notion being stressed throughout these first three examples, is that of continuations being "whatever remains to be executed", regardless of the abstraction level at which we decide to operate in.

Before dealing with more interesting stuff, the final example displays some more key properties of continuations.

Example 4: Conditional branches

Consider the code listing below. What is the continuation when line 1 is the redex? Is it necessary to know the result of rand() % 2 to determine the continuation? 

1: if (rand() % 2) {
2:   return foo();
3: } else {
4:   return bar();
5: }

This is a tricky question. There is no such thing as the continuation at this point in the execution, but rather two (!) continuations. After evaluating the conditional, one continuation is discarded and the other one is applied.

This example, short as it is, illustrates three more properties of continuations: (1) there is not necessarily one continuation at any given time; (2) continuations do not have to be applied, they can be discarded; and (3) a continuation may be applied or discarded based on runtime information.

Continuation Passing Style

Continuations as shown in the examples so far are not very interesting. We have identified them as part of the structure of execution state, but we cannot really do anything with them.

The issue here is that C++ has no language construct that allows us to treat continuations as any other kind of object in the language (some languages do have such a construct, see call/cc in Scheme). What we do have in C++ are function objects which can be passed around as arguments to functions. So we are going to apply the following program transformation throughout the whole program:

  1. Start from the beginning of the program
  2. Recognize the redex and its continuation.
  3. Replace the redex by a CPS function (see Listing 4). This function:
    1. Takes the parameters needed to execute the redex.
    2. Takes one extra invocable parameter per continuation. These are referred to as callbacks.
    3. Returns the result of applying only one of the callbacks to the evaluated redex.
  4. Invoke the CPS function with the arguments that allow the execution of the redex and one lambda per callback argument. Each lambda is associated to one of the continuations in the original code. If the associated continuation is empty, then the body of the lambda just returns its argument (i.e., it is the identity function). Otherwise, the body of the lambda corresponds to the steps of the associated continuation (see Listing 5).
  5. For each non-identity lambda created in step 4, repeat from step 2 using as starting point the first statement of the lambda.

The resulting code is said to be written in Continuation Passing Style (CPS). The algorithm just described is the CPS transform: a mapping from direct style (the usual way in which code is written) to CPS. 

1: // Original code: Direct Style
2: double sq(double x) { return x * x; }
3: 
4: // After step 3: Continuation Passing Style
5: auto sq(double x, auto cc) { return cc(x * x); }

1: // Original code: Direct Style
2: auto sqx = sq(x);
3: return foo(sqx);
4: 
5: // After step 4: Continuation Passing Style
6: return sq(x, [&](double sqx) { return foo(sqx); });

Step 5 states the iteration tactic of the transformation. To illustrate the result of such iteration, let us apply the procedure to the hypotenuse example – extended in Listing 6 with the definitions of sq, add, and sqr. 

1: double sq(double x) { return x * x; }
2: double add(double x, double y) { return x + y; }
3: double sqr(double x) { return sqrt(x); }
4: double hypotenuse(double x, double y) {
5:   auto sqx = sq(x);
6:   auto sqy = sq(y);
7:   auto r = add(sqx, sqy);
8:   return sqr(r);
9: }

This yields 

 1: double sq(double x, auto cc) { return cc(x * x); }
 2: double add(double x, double y, auto cc) { return cc(x + y); }
 3: double sqr(double x, auto cc) { return cc(sqrt(x)); }
 4: double hypotenuse(double x, double y, auto cc) {
 5:   return sq(x, [&](double sqx) {
 6:     return sq(y, [&](double sqy) {
 7:       return add(sqx, sqy, [&](double r) {
 8:         return sqr(r, cc);
 9:       });
10:     });
11:   });
12: }

If we bare with the ugliness of the code of Listing 7 for a second, we may notice that callbacks give us a way to deal with continuations as first-class objects. Having the continuation as an object allows us to do whatever one would do with an object – for example, store it in a queue, call it a task queue.

Of course one does not perform all of this callback ritual for silly arithmetic expressions, but rather when the redex can be resolved asynchronously. In such cases it is beneficial to place the callback in a data structure (queue) so that the program can do other stuff while the redex is executed. Once completion of the redex is signaled (somehow) and the result is gathered (somehow), the stored callback can be retrived and applied to the result of the redex.

What about main

In the ideal CPS world, everything in a program that is written in CPS takes these callback arguments (there can be more than one callback, see Example 4 and apply the CPS transform). But most of us have to deal with main being the entry point of our programs. The signature of main cannot be modified, putting it at odds with our idealized CPS world. The solution is simple: main acts as a barrier between the CPS world and the direct style world. 

void main() {
  std::optional<double> result;
  hypotenuse(2.0, 3.0, [&](double res) { result = res; });
  std::println("{}", *result);
}

Breaking the ideal CPS world feels a bit dirty. This is C++, we should be used to this feeling.

From CPS to std::execution

We are still a couple of program transformations away from the simplified std::execution framework that was promised by the introduction of this post. The remaining ones are algorithimically less contrived that the CPS transform, but provide relevant features to the framework.

Currying the callback arguments

The CPS function, created at step 3 of the CPS transform, holds two kinds of parameters:

  1. The data that allows the execution of the redex.
  2. The callbacks representing the continuations of the redex.

The purpose of the next transformation is to refactor CPS functions in order gain a clear separation between these two kinds of arguments. Currying the callback arguments achieves this goal (see Listing 9 and 10). 

1: // CPS
2: auto sq(double x, auto cc) { return cc(x * x); }
3: 
4: // Curried CPS
5: auto sq(double x) { return [=](auto cc) { return cc(x * x); }; }  

1: // CPS
2: return sq(x, [&](double sqx) { return foo(sqx); });
3: 
4: // Curried CPS
5: return sq(x)([&](double sqx) { return foo(sqx); });

Currying the CPS hypotenuse example of Listing 7, we obtain the following. 

 1: double sq(double x) { return [=](auto cc) { return cc(x * x); }; }
 2: double add(double x, double y) { return [=](auto cc) { return cc(x + y); }; }
 3: double sqr(double x) { return [=](auto cc) { return cc(sqrt(x)); }; }
 4: double hypotenuse(double x, double y) {
 5:   return [=](auto cc) {
 6:     return sq(x, [&](double sqx) {
 7:       return sq(y, [&](double sqy) {
 8:         return add(sqx, sqy, [&](double r) {
 9:           return sqr(r, cc);
10:         });
11:       });
12:     });
13:   };
14: }

If we bare with the ugliness of the code above for a second, we may notice that currying does indeed achieve a clear split between parameters used by the redex and the callbacks that represent the continuations.

Invoking a function written in curried CPS3 is two stepped:

  1. The curried CPS function is partially applied to the redex arguments.
  2. The partially applied CPS function is applied to the callbacks.

We can also think of the invocation of curried CPS functions in terms of finite state machines (FSM):

  • When the curried CPS function has not yet been applied, the FSM is in a non-configured state.
  • When the curried CPS function is partially applied to the redex arguments, the FSM transitions to a disconnected state. At this point the redex does not begin execution, but all the information needed to do so is available.
  • Finally, when the partially applied CPS function is appiled to the remaining callback arguments, the FSM transitions to the started state. At this point execution of the redex begins. Once the redex is resolved, one of the callbacks is applied to its result.

Summarizing, before currying each CPS function required us to inspect its parameter list to figure out which parameters are required by the redex and which are callbacks. Now this is always known from the structure of the curried CPS functions. This uniform shape – shared by every curried CPS function – is really useful for the sorts of generic programming that is heavily used throughout std::execution.
