This post is the first entry in a series of posts dissecting C++ std::execution: the framework for asynchronous computation proposed for standardization. The main purpose of the series is to develop an understanding of std::execution's API and (my understanding of) the rationale behind it from first principles. Additionally, those who have already studied std::execution and found themselves in one of the first four stages of grief when analyzing the meaning of

  • "Senders represent pending work",
  • "Senders compose",
  • "Users rarely need to care about receivers", or
  • "let_value is just the bind operator of the Continuation monad",

may find this series useful to reach the acceptance1 stage.

We begin with the bare basics: continuations and the structure of computation under a simplified std::execution framework. We will add complexity to the framework as the series progresses, slowly converging to std::execution as proposed for standardization.

Computation and continuations

A computation can be intuitively defined as a process by which some inputs are converted into some outputs by executing a set of steps one after the other2. At any given time, the execution state of a computation can be subdivided into two: already executed steps and to-be-executed steps. To-be-executed steps can be further subdivided into the next immediate step to be executed, and the remaining non-immediate steps to be executed. The former step is known as the reducible expression and the latter steps conform what is referred to as the continuation.

The wording of the previous paragraph is intentionally vague. This is to prevent its understanding in terms that are too concrete for the level of reasoning we are aiming for. If in place of "steps" the paragraph used "instructions", we could easily (mis)understand reducible expressions and continuations to be defined in terms of CPU instructions. While CPU instructions could be thought of as steps, they are far from the only granularity level at which we would like to apply these ideas. The following examples should clarify the situation.

Example 1: Arithmetic expressions

Given the expression 1 + 2 * 3, the usual precedence rules tell us that the first step to be executed is 2 * 3. That is, 2 * 3 is the reducible expression and 1 + ... is the continuation.

While 2 * 3 is executed, the result of 1 + ... remains undetermined. We can think of 1 + ... as being suspended until the result of 2 * 3 is available. Once the result is available we "fill" the ellipsis of 1 + ... to obtain 1 + 6. We will refer to this "filling" as applying the continuation.

The expression we were left with, 1 + 6, has one single step to be executed and an empty continuation (no non-immediate next steps). In other words, after executing the reducible expression, the computation is done.

This silly example already shows a key property of continuations: they are comprised not solely of operational descriptions (+), but also of the data needed to execute these operations once the continuation is applied (1).

Example 2: Subsequent statements

There is no reason to limit our understanding of steps of a computation to arithmetic expressions. We could understand steps to be statements, and the order of execution would be the usual top-to-bottom statement execution.

Consider 

1: auto sqx = x * x;
2: auto sqy = y * y;
3: auto r = sqx + sqy;

A valid execution state has line 1 as its reducible expression and statements of lines 2 and 3 conform the continuation.

Disregarding practicality, it does not really matter how granular a step is when discussing continuations as long as we are consistent.

Example 3: Function boundaries

So far none of the examples have function calls in them, but this does not have to be the case. Given the function hypotenuse as defined below 

1: double hypotenuse(double x, double y) {
2:   auto sqx = sq(x);
3:   auto sqy = sq(y);
4:   auto r = add(sqx, sqy);
5:   return sqrt(r);
6: }

if sq(x) is the reducible expression of the execution state being considered, then the continuation is conformed by the assignment to sqx, statements of lines 5, 6 and 7, and whatever the caller of hypotenuse does after hypotenuse returns. Notice that we treated sq(x) as a single step, ignoring the complexity of the implementation of sq.

The examples so far are stressing the idea that a continuation is "whatever remains to be executed". This holds regardless of the granularity level at which we decide to operate in.

The final example focuses on other relevant properties of continuations.

Example 4: Conditional branches

Consider the code listing below, what is the continuation when line 1 is the reducible expression? Is it necessary to know the result of rand() % 2 to determine the continuation? 

1: if (rand() % 2) {
2:   return foo();
3: } else {
4:   return bar();
5: }

This is a tricky question. There is no such thing as the continuation at this point in the execution, but rather two (!) continuations. After evaluating the conditional, one continuation is discarded and the other one is applied.

This example illustrates three more properties of continuations: (1) there is not necessarily one continuation at any given time; (2) continuations do not have to be applied, they can be discarded; and (3) a continuation may be applied or discarded based on runtime information.

Continuation Passing Style

Continuations as shown in the examples so far are not very interesting. We have identified them as part of the structure of execution state, but we cannot really do anything with them.

The issue here is that C++ has no language construct that allows us to treat continuations as any other kind of object in the language (some languages do have such a construct, see call/cc in Scheme). What we do have in C++ are function objects which can be passed around as arguments to functions – this is made easier by the existence of lambdas. So what we are going to do is the following

  1. Start from the beginning of the program
  2. Recognize the reducible expression and its continuation.
  3. Replace the reducible expression by a function that
    1. Takes the arguments needed to execute the reducible expression.
    2. Takes one extra argument per continuation, which are function objects.
    3. Returns the result of applying one of the arguments added by step 3.2 to the reducible expression.
  4. Invoke this new function with the required arguments and as many lambdas as continuations. The body of these lambdas correspond to the steps of the continuation to which they are associated.
  5. For each non-empty lambda created in step 4, repeat the process from step 2 starting from the reducible expression of an execution that begins at the first statement of the lambda.

To illustrate, applying this process to 

1: double sq(double x) { return x * x; }
2: double add(double x, double y) { return x + y; }
3: double sqr(double x) { return sqrt(x); }
4: double hypotenuse(double x, double y) {
5:   auto sqx = sq(x);
6:   auto sqy = sq(y);
7:   auto r = add(sqx, sqy);
8:   return sqr(r);
9: }

yields 

 1: double sq(double x, auto cc) { return cc(x * x); }
 2: double add(double x, double y, auto cc) { return cc(x + y); }
 3: double sqr(double x, auto cc) { return cc(sqrt(x)); }
 4: double hypotenuse(double x, double y, auto cc) {
 5:   return sq(x, [&](double sqx) {
 6:     return sq(y, [&](double sqy) {
 7:       return add(sqx, sqy, [&](double r) {
 8:         return sqr(r, cc);
 9:       });
10:     });
11:   });
12: }

If we bare with the ugliness of the resulting code for a second, we can notice that this process has effectively given us a way to deal with continuations as first-class objects, referred to as callbacks. The technique that enables this is called Continuation Passing Style (CPS) and the algorithm described above is the CPS transform.

Having the continuation as an object allows us to store it (for example, in a queue). Of course usually one does not perform all this callback ritual for silly arithmetic expressions, but rather when the reducible expression is resolved asynchronously. In such cases, it is beneficial to place the continuation in a data structure (queue) so that the program can do other stuff while it waits for the completion of the reducible expression to be signaled in some form.

What about main

In our ideal CPS world, everything in a program that is written in CPS style takes these callback arguments (there can be more than one callback, see No description for this link and apply the CPS transform). But most of us have to deal with main being the entry point of our programs. The signature of main cannot be modified, putting it at odds with our idealized CPS world. The solution is simple: main acts as a barrier between the CPS world and the old world. 

void main() {
  std::optional<double> result;
  hypotenuse(2.0, 3.0, [&](double res) { result = res; });
  std::println("{}", *result);
}

Breaking the ideal CPS world feels a bit dirty. This is C++, we are used to this feeling.
