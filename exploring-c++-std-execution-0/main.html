This post is the first entry in a series of posts dissecting C++ std::execution: the framework for asynchronous computation proposed for standardization. The main purpose of the series is to develop an understanding of std::execution's API and (my understanding of) the rationale behind it from first principles. Additionally, those who have already studied std::execution and found themselves in one of the first four stages of grief when analyzing the meaning of

  • "Senders represent pending work",
  • "Senders compose",
  • "Users rarely need to care about receivers", or
  • "let_value is just the bind operator of the Continuation monad",

may find this series useful to reach the acceptance1 stage.

We begin with the bare basics: continuations and the structure of computation under a simplified std::execution framework. We will add complexity to the framework as the series progresses, slowly converging to std::execution as proposed for standardization.

Computation and continuations

A computation can be intuitively defined as a process by which some inputs are converted into some outputs by executing a set of steps one after the other2. At any given time, the execution state of a computation can be subdivided into two: already executed steps and to-be-executed steps. To-be-executed steps can be further subdivided into the next immediate step to be executed, and the remaining non-immediate steps to be executed. The former step is known as the reducible expression (redex for short) and the latter steps conform what is referred to as the continuation.

The wording of the previous paragraph is intentionally vague. This is to prevent its understanding in terms that are too concrete for the level of reasoning we are aiming for. If in place of the word "steps" the paragraph used the word "instructions", then for us programmers this could be easily (mis)understood as a definition of reducible expressions and continuations in terms of CPU instructions. While CPU instructions could be thought of as steps, they are far from the only abstraction level at which we would like to apply these ideas. The following examples should clarify the situation.

Example 1: Arithmetic expressions

Given the expression 1 + 2 * 3, the usual precedence rules tell us that the first step to be executed is 2 * 3. That is, 2 * 3 is the redex and 1 + ... is the continuation.

While 2 * 3 is executed, the result of 1 + ... remains undetermined. We can think of 1 + ... as being suspended until the result of 2 * 3 is available. Once the result is available, we substitute the ellipsis in 1 + ... to obtain 1 + 6. This substitution process is denoted as applying the continuation.

The expression we are left with, 1 + 6, has one single step to be executed and an empty continuation (no non-immediate next steps). In other words, after executing the redex, the computation is done.

This silly example already shows a key property of continuations: they are comprised not solely of operational descriptions (+), but also of the data needed to execute these operations once the continuation is applied (1).

Example 2: Subsequent statements

There is no reason to limit the abstraction level of "steps" just to arithmetic expressions. We could take a step to be a statement. The order of execution is given by the usual top-to-bottom statement execution.

Consider 

1: auto sqx = x * x;
2: auto sqy = y * y;
3: auto r = sqx + sqy;

A valid execution state has the statement in line 1 as its redex and statements of lines 2 and 3 conform its continuation.

Disregarding practicality, it does not really matter how granular (abstract) a step is when discussing continuations as long as we are consistent.

Example 3: Function boundaries

So far none of the examples have function calls in them, but this does not have to be the case. Given the function hypotenuse as defined below 

1: double hypotenuse(double x, double y) {
2:   auto sqx = sq(x);
3:   auto sqy = sq(y);
4:   auto r = add(sqx, sqy);
5:   return sqrt(r);
6: }

If sq(x) is the redex of an execution state, then its continuation is conformed by the assignment to sqx, statements of lines 5, 6 and 7, and whatever the caller of hypotenuse does after hypotenuse returns. Notice that we treated sq(x) as a single step, ignoring the complexity of the implementation of sq.

The notion being stressed throughout these first three examples, is that of continuations being "whatever remains to be executed", regardless of the abstraction level at which we decide to operate in.

Before dealing with more interesting stuff, the final example displays some more key properties of continuations.

Example 4: Conditional branches

Consider the code listing below. What is the continuation when line 1 is the redex? Is it necessary to know the result of rand() % 2 to determine the continuation? 

1: if (rand() % 2) {
2:   return foo();
3: } else {
4:   return bar();
5: }

This is a tricky question. There is no such thing as the continuation at this point in the execution, but rather two (!) continuations. After evaluating the conditional, one continuation is discarded and the other one is applied.

This example, short as it is, illustrates three more properties of continuations: (1) there is not necessarily one continuation at any given time; (2) continuations do not have to be applied, they can be discarded; and (3) a continuation may be applied or discarded based on runtime information.

Continuation Passing Style

Continuations as shown in the examples so far are not very interesting. We have identified them as part of the structure of execution state, but we cannot really do anything with them.

The issue here is that C++ has no language construct that allows us to treat continuations as any other kind of object in the language (some languages do have such a construct, see call/cc in Scheme). What we do have in C++ are function objects which can be passed around as arguments to functions. So we are going to apply the following program transformation throughout the whole program:

  1. Start from the beginning of the program
  2. Recognize the redex and its continuation.
  3. Replace the redex by a CPS function (see Listing 4). This function:
    1. Takes the parameters needed to execute the redex.
    2. Takes one extra invocable parameter per continuation. These are referred to as callbacks.
    3. Returns the result of applying only one of the callbacks to the evaluated redex.
  4. Invoke the CPS function with the arguments that allow the execution of the redex and one lambda per callback argument. Each lambda is associated to one of the continuations in the original code. If the associated continuation is empty, then the body of the lambda just returns its argument (i.e., it is the identity function). Otherwise, the body of the lambda corresponds to the steps of the associated continuation (see Listing 5).
  5. For each non-identity lambda created in step 4, repeat from step 2 using as starting point the first statement of the lambda.

The resulting code is said to be written in Continuation Passing Style (CPS). The algorithm just described is the CPS transform: a mapping from direct style (the usual way in which code is written) to CPS. 

// Original code: Direct Style
double sq(double x) { return x * x; }

// After step 3: Continuation Passing Style
auto sq(double x, auto cc) { return cc(x * x); }

// Original code: Direct Style
auto sqx = sq(x);
return foo(sqx);

// After step 4: Continuation Passing Style
return sq(x, [&](double sqx) { return foo(sqx); });

Step 5 states the iteration tactic of the transformation. To illustrate the result of such iteration, let us apply the procedure to the hypotenuse example – extended in Listing 6 with the definitions of sq, add, and sqr. 

double sq(double x) { return x * x; }
double add(double x, double y) { return x + y; }
double sqr(double x) { return sqrt(x); }
double hypotenuse(double x, double y) {
  auto sqx = sq(x);
  auto sqy = sq(y);
  auto r = add(sqx, sqy);
  return sqr(r);
}

This yields 

double sq(double x, auto cc) { return cc(x * x); }
double add(double x, double y, auto cc) { return cc(x + y); }
double sqr(double x, auto cc) { return cc(sqrt(x)); }
double hypotenuse(double x, double y, auto cc) {
  return sq(x, [&](double sqx) {
    return sq(y, [&](double sqy) {
      return add(sqx, sqy, [&](double r) {
        return sqr(r, cc);
      });
    });
  });
}

If we bare with the ugliness of the code above for a second, we may notice that callbacks give us a way to deal with continuations as first-class objects. Having the continuation as an object allows us to do whatever one would do with an object – for example, store it in a queue, call it a task queue.

Of course one does not perform all of this callback ritual for silly arithmetic expressions, but rather when the redex can be resolved asynchronously. In such cases it is beneficial to place the callback in a data structure (queue) so that the program can do other stuff while the redex is executed. Once completion of the redex is signaled (somehow) and the result is gathered (somehow), the stored callback can be retrived and applied to the result of the redex.

What about main

In the ideal CPS world, everything in a program that is written in CPS takes these callback arguments (there can be more than one callback, see Example 4 and apply the CPS transform). But most of us have to deal with main being the entry point of our programs. The signature of main cannot be modified, putting it at odds with our idealized CPS world. The solution is simple: main acts as a barrier between the CPS world and the direct style world. 

void main() {
  std::optional<double> result;
  hypotenuse(2.0, 3.0, [&](double res) { result = res; });
  std::println("{}", *result);
}

Breaking the ideal CPS world feels a bit dirty. This is C++, we should be used to this feeling.

From CPS to std::execution

We are still a couple of program transformations away from the simplified std::execution framework that was promised by the introduction of this post. The remaining ones are algorithmically less contrived than the CPS transform, but provide relevant features to the framework.

Currying the callback arguments

The CPS function, created at step 3 of the CPS transform, holds two kinds of parameters:

  1. The data that allows the execution of the redex.
  2. The callbacks representing the continuations of the redex.

The purpose of the next transformation is to refactor CPS functions in order gain a clear separation between these two kinds of arguments. Currying the callback arguments achieves this goal (see Listing 9 and 10). 

// CPS
auto sq(double x, auto cc) { return cc(x * x); }

// Curried CPS
auto sq(double x) { return [=](auto cc) { return cc(x * x); }; }  

// CPS
return sq(x, [&](double sqx) { return foo(sqx); });

// Curried CPS
return sq(x)([&](double sqx) { return foo(sqx); });

An important detail (at risk of being lost to its concise syntax) is that the implementation of the curried CPS function (Listing 9) returns a lambda that captures the function's arguments by value. There is no other choice than to capture by value because references to the arguments dangle as soon as the curried CPS function returns. On the other hand, the call-site (Listing 10) can create a callback that captures by reference because continuation passing style ensures the callback is invoked before the call expression is fully evaluated.

Currying the CPS hypotenuse example of Listing 7, yields the following. 

auto sq(double x) { return [=](auto cc) { return cc(x * x); }; }
auto add(double x, double y) { return [=](auto cc) { return cc(x + y); }; }
auto sqr(double x) { return [=](auto cc) { return cc(sqrt(x)); }; }
auto hypotenuse(double x, double y) {
  return [=](auto cc) {
    return sq(x)([&](double sqx) {
      return sq(y)([&](double sqy) {
        return add(sqx, sqy)([&](double r) {
          return sqr(r)(cc);
        });
      });
    });
  };
}

If we bare with the ugliness of the code above for a second, we may notice that currying does indeed achieve a clear split between parameters used by the redex and the callbacks that represent the continuations.

Invoking a function written in curried CPS3 is two stepped:

  1. The curried CPS function is partially applied to the redex arguments.
  2. The partially applied curried CPS function is applied to the callbacks and execution of the redex begins.

We can also think of the invocation of curried CPS functions in terms of finite state machines (FSM):

  • When the curried CPS function has not yet been applied, the FSM is in a non-configured state.
  • When the curried CPS function is partially applied to the redex arguments, the FSM transitions to a disconnected state. At this point the redex does not begin execution, but all the information needed to do so is available.
  • Finally, when the partially applied CPS function is appiled to the remaining callback arguments, the FSM transitions to the started state. At this point execution of the redex begins. Once the redex is resolved, one of the callbacks is applied to its result.

Summarizing, before currying each CPS function required us to inspect its parameter list to figure out which parameters are required by the redex and which are callbacks. Now this is always known from the structure of the curried CPS functions. Having a uniform shape is really useful for the sorts of generic programming that is heavily used throughout std::execution.

Laziness and thunks

Almost all introductions to std::execution claim its laziness fairly early on. The purpose of the transformation presented in this section is to grant curried CPS functions the property of lazy execution.

The rationale behind wanting laziness in an asynchronous programming framework has been thoroughly discussed and it would be too large of a tangent for this post. In short, it eases the development and correctness verification of asynchronous programming patterns – we have not defined any such pattern yet, but think of stuff like awaiting the result of several computations that were logically launched simultaneously. This Lewis Baker talk on structured concurrency covers the issue quite well.

The transformation relies on thunks to achieve the effect of attaching callbacks without evaluating the redex. A thunk is a concept independent of all the CPS topics discussed so far. Broadly speaking, it is a closure with an empty parameter list. This enables deferring the execution of whatever expression it encloses until the thunk is invoked with an empty argument list. The transformation, applied to curried CPS functions is depicted in the listings below. 

// Curried CPS
auto sq(double x) { return [=](auto cc) { return cc(x * x); }; }

// Lazy curried CPS
auto sq(double x) { return [=](auto cc) { return [=]() { return cc(x * x); }; }; }    

// Curried CPS
return sq(x)([&](double sqx) { return foo(sqx); });

// Lazy curried CPS
return sq(x)([&](double sqx) { return foo(sqx); })();

Just like the curried callback parameter in the previous section, the thunk must capture by value. This is to prevent dangling of both redex and callback arguments. Call-site rules change, however. Before thunks callbacks created at call-site could capture by reference safely. Now only the caller that invokes the thunk can do so. The problematic case is depicted in Listing 14. 

/* thunk_type */ auto sq_plus(double x, double y) {
  return sq(x)([&](double sqx) { return sqx + y; });
} // ERROR! The callback has not been invoked yet, `y` has been destructed

In code that executes a sequence of lazy curried CPS functions, thunks require an invocation after each callback attachment. This leads to a sort of chain reaction through the sequenced operations: the completion of one operation immediately starts the next one, as shown in Listing 15. 

auto sq(double x) { return [=](auto cc) { return [=]() { return cc(x * x); }; }; }
auto add(double x, double y) { return [=](auto cc) { return [=]() { return cc(x + y); }; }; }
auto sqr(double x) { return [=](auto cc) { return [=]() { return cc(sqrt(x)); }; }; }
auto hypotenuse(double x, double y) {
  return [=](auto cc) {
    return [=]() {
      return sq(x)([&](double sqx) {
        return sq(y)([&](double sqy) {
          return add(sqx, sqy)([&](double r) {
            return sqr(r)(cc)();
          })();
        })();
      })();
    };
  };
}

If we bare with the ugliness of the code above for a second, we may notice that these are lazily composed (sequenced) operations. Similar in spirit to what std::execution promises.

Invoking a function written in lazy curried CPS4 is three stepped:

  1. The lazy curried CPS function is partially applied to the redex arguments.
  2. The partially applied lazy curried CPS function is applied to the callbacks and returns a thunk.
  3. The returned thunk is invoked and execution of the redex begins.

We can also think of the invocation of lazy curried CPS functions in terms of finite state machines (FSM):

  • When the lazy curried CPS function has not yet been applied, the FSM is in a non-configured state.
  • When the lazy curried CPS function is partially applied to the redex arguments, the FSM transitions to a disconnected state. At this point the redex does not begin execution, but all the information needed to do so is available.
  • When the partially applied lazy curried CPS function is appiled to the remaining callback arguments, the FSM transitions to the connected state and a thunk is created to defer execution.
  • Finally, when the thunk is invoked, the execution of the redex begins. Once the redex is resolved, one of the callbacks is applied to its result.

At this point the simplified framework has almost everything it needs, functionally at least. We still need to deal with its ugliness, as it would be very naive to expect code like that of Listing 15 to be maintainable or even pleasant to read.

Compositional patterns

In Elements of Programming, a computational basis for a type is defined as the finite set of procedures that enable the construction of any other procedure on the type. In other words, these procedures can be functionally composed to obtain any other procedure on the type. For example, for unsigned integers a computational basis could be zero, operator==, and successor functions (let us ignore the efficiency aspect for now).

We can reformulate the notion of computational basis for types to obtain the notion of computational basis for computation itself. The procedures on computations are simply the compositional patterns that enable constructing larger computations from smaller ones. A computational basis for computation is a finite set of compositional patterns from which every other compositional pattern can be obtained 5.

Since the redex and continuations we have been abstracting over are a way to represent computations, these facts about compositional patterns and computational basis apply to the framework we have developed throughout the last few sections. We can readily identify a basis in Listing 15: lifting and sequencing. We will use these patterns to remove noise from the running example, making it more maintainable and aesthetically pleasing.

Lifting

Lifting in the context of CPS occurs whenever we want to carry some data from the direct style world to the CPS world. In Listing 15 this occurs to the arguments of hypotenuse, which are lifted in sq, add, sqr before their usage in the redex expressions. The general pattern is implemented in the listing below. 

auto just(auto value) {
  return [=](auto cc) {
    return [=]() {
      return cc(value);
    };
  };
}

The code is straightforward, the function just is in lazy curried CPS and it simply captures a value and forwards it to the user-provided callback.

Sequencing

A basic compositional pattern between computations is using the outputs of one computation as the inputs of the next computation. The function in Listing 17, let_value, captures this pattern. 

auto let_value(auto f_disconnected, auto g_nonconfig) {
  return [=](auto cc) {
    return [=]() {
      auto f_connected = f_disconnected([=](auto f_ret) {
        auto g_disconnected = g_nonconfig(f_ret);
        auto g_connected = g_disconnected(cc);
        return g_connected();
      });
      return f_connected();
    };
  };
}

The names chosen for the parameters and variables of Listing 17 reference the states of the state machine used to understand the application of lazy curried CPS in the previous section. Both parameters are functions written in lazy curried CPS, but f_disconnected has been already partially applied to its redex arguments by the time let_value is applied to it, while g_nonconfig has no arguments available to it. When started, let_value executes the computation enclosed by f_disconnected and forwards its result as the redex arguments of g_nonconfig, obtaining g_disconnected. The callback argument of let_value is then attached to g_disconnected, and the resulting thunk is immediately invoked.

With let_value and just at hand, we can already improve the readability of the running example quite a bit. Listing 18 shows the refactor of sq. 

// Lazy curried CPS
auto sq(double x) { return [=](auto cc) { return [=]() { return cc(x * x); }; }; }

// Lazy curried CPS with let_value and just
auto sq(double x) {
  return let_value(just(make_pair(x, x)), [](auto xy) { return just(mul_(xy)); });
}
// where mul_ is:
auto mul_(auto xy) { return std::apply(std::multiplies{}, xy); }

Now the callback argument and the two lambdas corresponding to the currying of the callback parameter and the thunk are implicit. But this can be further improved. The usage pattern of mul_ is common to sq, add, sqr and it is captured by the then algorithm. This algorithm can be seen as a sort of lifting, like just, but for mapping functions (functions suitable for std::transform). 

auto then(auto f_disconnected, auto map) {
  return let_value(f_disconnected, [=](auto f_ret) {
    return [=](auto cc) {
      return [=]() {
        return cc(map(f_ret));
      };
    };
  });
}

The running example, after applying these compositional patterns, is shown in Listing 20. 

// mul_, add_, sqrt_ are the usual arithmetic operations.
// binary operations taking a pair instead of two args

auto sq(double x) { return then(just(make_pair(x, x)), mul_); }
auto add(double x, double y) { return then(just(make_pair(x, y)), add_); }
auto sqr(double x) { return then(just(x), sqrt_); }
auto hypotenuse(double x, double y) {
  return let_value(sq(x), [=](double sqx) {
    return let_value(sq(y), [=](double sqy) {
      return let_value(add(sqx, sqy), [=](double r) {
        return sqr(r);
      });
    });
  });
}

Simplified std::execution

Compositional patterns over lazy curried CPS, as developed over the last sections, are analogous in many ways to the control flow mechanism proposed by std::execution:

  • Callbacks are analogous to receivers.
    • Invoking operator() / set_value on them propagates results through the execution.
  • Thunks are analogous to operation state.
    • They ensure redex arguments' lifetime until completion.
    • Once called / start-ed the redex is executed.
  • Lazy curried CPS functions are analogous to senders.
    • They enclose computation, but do not execute it (lazy).
    • They are connect-ed to a callback / receiver.
  • Compositional patterns are analogous to sender algorithms.
    • They are parameterized by lazy curried CPS functions / senders and return lazy curried CPS functions / senders.
    • They describe the way in which computations are composed.

We now translate the lazy curried CPS compositional patterns into a structure more alike that of std::execution's sender algorithms. As a rule of thumb:

  • Appearances of lazy curried CPS functions are replaced by appearances of senders.
    • Wherever a lazy curried CPS function was applied to redex arguments, a sender is created using the same arguments.
    • Wherever a callback was passed as an argument to a disconnected lazy curried CPS function, a receiver is passed as the argument of a sender's connect member function.
  • Appearances of thunks are replaced by appearances of operation states.
    • Wherever a thunk was invoked, an operation state is start-ed.
  • Appearances of callbacks get replaced by appearances of receivers.
    • Wherever a callback was invoked, a receiver's set_value is invoked.
  • Wherever an argument was captured, a member variable is initialized.

Simplified just

The most basic sender algorithm is just. This algorithm is what std::execution refers to as a sender factory, meaning that it does not have any input sender and it produces a sender. Input senders are typically denoted as children senders. The parent sender in this context is the sender returned by the sender algorithm that takes senders as input. The largely common case (but not universal) in std::execution is that computation represented by children senders is executed before the computation represented by the parent sender. In any case, just has no children senders, so by definition nothing executes before it. 

namespace just_ {
  template<typename Rcv, typename T>
  struct op {
    Rcv next;
    T x;
    void start() { next.set_value(x); }
  };

  template<typename T>
  struct snd {
    T x;
    template<typename Rcv>
    op<Rcv, T> connect(Rcv next) { return {next, x}; }
  };
} // namespace just_

static constexpr auto just = [](auto x) { return just_::snd(x); };

The code in Listing 21 above is a direct application of the recently stated rule of thumb to Listing 16. Because just_::snd has no children senders, it does not make sense for there to be a receiver just_::rcv – there are no children senders to which it could be connected to. In more general terms, a receiver is associated to a sender when the computation represented by the sender requires input data. This is the case for the then algorithm, which we develop next.

Simplified then

namespace then_ {
  template<typename Op>
  struct rcv {
    Op* op;
    void set_value(auto x) { return op->complete(x); }
  };

  template<typename Rcv, typename Prev, typename F>
  struct op {
    Rcv next;
    Prev prev;
    F f;

    void start() {
      auto op = prev.connect(rcv<op>{this});
      op.start();
    }

    void complete(auto x) {
      next.set_value(f(x));
    }
  };

  template<typename Prev, typename F>
  struct snd {
    Prev prev;
    F f;
    template<typename Rcv>
    op<Rcv, Prev, F> connect(Rcv next) { return {next, prev, f}; }
  };
} // namespace then_

static constexpr auto then = [](auto prev, auto f) {
  return then_::snd(prev, f);
};

Simplified let_value

namespace let_value_ {
  template<typename Op>
  struct intermediate_rcv {
    Op* op;
    void set_value(auto x) { return op->complete_intermediate(x); }
  };

  template<typename Rcv, typename Prev, typename MakeSnd>
  struct op {
    Rcv next;
    Prev prev;
    MakeSnd make_snd;

    void start() {
      auto op1 = prev.connect(intermediate_rcv<op>{this});
      op1.start();
    }

    void complete_intermediate(auto x) {
      auto op2 = make_snd(x).connect(next);
      op2.start();
    }
  };

  template<typename Prev, typename MakeSnd>
  struct snd {
    Prev prev;
    MakeSnd make_snd;

    template<typename Rcv>
    op<Rcv, Prev, MakeSnd> connect(Rcv next) { return {next, prev, make_snd}; }
  };
} // namespace let_value_

static constexpr auto let_value = [](auto prev, auto make_snd) {
  return let_value_::snd(prev, make_snd);
};
